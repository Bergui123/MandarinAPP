# Talk Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a hands-free, voice-conversation "Talk" mode to the Mandarin app: the user speaks, on-device speech recognition transcribes it, DeepSeek decides the tutor's reply, on-device speech synthesis speaks it back — looping automatically like a phone call, usable with the iPhone locked, for sessions up to ~2 hours/day, cheaply.

**Architecture:** On-device STT → DeepSeek chat-completions (text only) → on-device TTS, looped. A bounded context (system prompt + known-word list + a periodically-updated running memory summary + last ~10-15 raw turns) keeps every request small regardless of session length. Words DeepSeek teaches join the same tracked learned-word list the Practice screen already reads from, tagged inline in replies and parsed out before speaking.

**Tech Stack:** Expo/React Native (existing), a native speech-recognition library (new — exact package confirmed in Task 1), `expo-speech` (existing, already used for TTS), DeepSeek's chat-completions HTTP API (new, plain `fetch`, no SDK), Expo's built-in `.env` support for the API key.

**Spec:** `docs/superpowers/specs/2026-10-17-talk-mode-design.md`

## Global Constraints

- iOS background audio: `UIBackgroundModes: ["audio"]` required in `app.json`.
- Development build required for all of Talk mode — Expo Go cannot run it (native speech recognition). This dev environment is Linux: no local `expo run:ios`/Xcode. Builds happen via `eas build --profile development --platform ios`; the user installs and tests on their own physical iPhone.
- iPhone first. Android support for Talk mode is explicitly out of scope for this plan.
- DeepSeek API key lives in a git-ignored local `.env` (`EXPO_PUBLIC_DEEPSEEK_API_KEY`) — never committed, never hardcoded in a tracked file, no in-app settings screen.
- No live/real-time voice API (OpenAI Realtime, Gemini Live, or similar) anywhere in this feature — on-device STT/TTS only; DeepSeek is used for text exchange only.
- Per-DeepSeek-request context stays small by design: system prompt + known-word hanzi list + current memory summary + last ~10-15 raw turns only — never the full session transcript.
- No cap on how many new words Talk mode introduces per session; this is independent of and does not interact with Practice's one-new-character-per-day unlock.
- Conversation does not increment a word's write/speak rep counts — those only move from deliberate taps on the Practice screen, same as today.
- This project has no test framework installed (no Jest/Vitest). Do not add one for this feature. Verify pure-logic changes by seeding `AppState`-shaped JSON via the browser preview's `javascript_tool` (same technique already used to verify `progress.ts` and the character dataset earlier in this project) and inspecting the result via `console.log`/`read_page`/screenshot. Verify UI/integration changes via the existing manual browser-preview workflow. `npx tsc --noEmit` and `npx expo lint` must still pass before any task is considered done.

## Review Focus

- **DeepSeek request fails or times out mid-call** (network drop while driving): must not crash the app or leave it stuck silently listening forever — speak a short local fallback line and resume listening. Owned by Task 6.
- **Empty/silence transcript** (background noise, long pause, STT returns `""`): must not be sent to DeepSeek as a message — treat as a no-op and keep listening. Owned by Task 6.
- **Goodbye phrase appears mid-sentence rather than as a real sign-off** (e.g. the user mentions 再见 while asking what it means): the local end-of-call detection is a known-imperfect heuristic, not disguised as reliable — documented as such, with the manual End button as the dependable path. Owned by Task 6.
- **The same word gets "introduced" more than once** (DeepSeek re-teaches a word already tracked, whether from the static dataset or an earlier conversation): must not create a duplicate tracked entry. Owned by Task 3.
- **A conversation-sourced word's `hanzi` is multiple characters** (e.g. 知道): must render correctly (not clipped/overflowing) on both the Practice row and the quiz flashcard, which currently assume a single glyph. Owned by Task 8.
- **An incoming phone call interrupts an active Talk session**: must not crash or silently leave the app stuck mid-`'thinking'`/`'speaking'` after the interruption clears — pause cleanly and resume listening once the call ends. Owned by Task 6.

## Task 6: Talk session — the conversation loop

This is the core of the feature: turns `talk.tsx` from Task 1's bare mic test into the full hands-free conversation.

**Files:**
- Create: `src/hooks/use-talk-session.ts`
- Modify: `src/app/talk.tsx` (replace the minimal version from Task 1 with the full call UI)

**Interfaces:**
- Consumes: `useSpeechRecognition` (Task 1), `speak` (Task 4), `chatComplete`/`ChatMessage` (Task 5), `useAppState()`'s `addConversationWord`/`updateNotes`/`updateTalkMemory` and `state.learned`/`state.talkMemory` (Task 3).
- Produces: `type TalkState = 'idle' | 'listening' | 'thinking' | 'speaking'` and `useTalkSession(): { callState: TalkState; transcriptLog: { role: 'user' | 'assistant'; text: string }[]; startCall: () => void; endCall: () => void }` — consumed by `talk.tsx`.

- [ ] **Step 1: Define the system prompt as a constant in `use-talk-session.ts`**

Establishes: patient Mandarin tutor persona; speaks mostly Mandarin, slowly and in short sentences (a sentence or two per turn — this is spoken, not written); uses primarily words from the provided known-word list; introduces new vocabulary at a random, unforced cadence; when introducing a word not in the known-word list, wraps it inline as `⟦hanzi|pinyin|meaning⟧` at the point it's used in the sentence; answers the user's questions, and explains new words, in English when asked or when it would clearly help; never uses the `⟦...⟧` markup for a word already in the known-word list.

- [ ] **Step 2: Implement the known-word context block**

A function that takes `AppState['learned']` and returns a comma-separated string of each entry's `hanzi` (via `resolveCharacterDisplay`) — this is what gets embedded in the system prompt's known-word section per turn.

- [ ] **Step 3: Implement the new-word tag parser**

`parseNewWordTags(reply: string): { cleanText: string; newWords: { hanzi: string; pinyin: string; meaning: string }[] }`. Matches `⟦([^|⟧]+)\|([^|⟧]+)\|([^⟧]+)⟧` globally; `cleanText` is the reply with each match replaced by just its captured hanzi (so the sentence still reads naturally once spoken); `newWords` is the list of captured triples.

- [ ] **Step 4: Implement local end-of-call detection**

`isGoodbye(transcript: string): boolean` — a case-insensitive regex over a short fixed list (`再见|拜拜|goodbye|bye|结束|end call` or similar). Documented in a one-line comment as intentionally imprecise (Review Focus item: a mid-sentence mention is a known false-positive risk) — the manual End button in `talk.tsx` is the reliable path.

- [ ] **Step 5: Implement `useTalkSession`**

State: `callState`, `transcriptLog`, a ref holding the last ~10-15 raw turns (role/content pairs) for the next request's context, and a counter of exchanges since the last memory update.

`startCall()`: sets `callState: 'listening'`, starts `useSpeechRecognition`.

On each transcript from the recognition hook:
- If blank/whitespace-only, ignore and keep listening (Review Focus item: empty transcript).
- Else if `isGoodbye(transcript)`, speak a short fixed goodbye line via `speak`, flush a final memory update (Task 7's function), then set `callState: 'idle'` and stop recognition.
- Else: append to `transcriptLog` and the recent-turns ref, set `callState: 'thinking'`, build the message list (system prompt with the known-word block and current `talkMemory` + the recent-turns window + the new user message), call `chatComplete`. On success: run `parseNewWordTags` on the reply, call `addConversationWord` for each new word, append the reply to `transcriptLog`/recent-turns, set `callState: 'speaking'`, call `speak(cleanText, { rate: 0.75 })`, and once playback completes resume listening (`callState: 'listening'`). On failure (Review Focus item: DeepSeek request fails/times out): catch the error, speak a short fixed local fallback line (e.g. "Sorry, I'm having trouble connecting, let's try again"), and resume listening rather than getting stuck in `'thinking'`.

Every time the exchange counter crosses the threshold from Task 7, trigger (without blocking the loop) Task 7's memory-update call.

`endCall()`: stops recognition, flushes a final memory update, sets `callState: 'idle'`.

- [ ] **Step 6: Handle audio interruptions (e.g. an incoming phone call)**

Confirm, against the chosen STT library's docs and `expo-audio`/`expo-av`'s current interruption-handling API (per AGENTS.md — do not assume from memory), how to subscribe to an audio-session interruption. On interruption start: stop recognition and any in-progress `speak()`, set `callState: 'idle'` rather than leaving it stuck in `'thinking'`/`'speaking'`. On interruption end: if the call is still active (user hasn't tapped End), resume listening; if `endCall()` was called during the interruption, do nothing further.

- [ ] **Step 7: Rebuild `talk.tsx` around the hook**

A large Start/End button reflecting `callState` (e.g. different label/color for listening/thinking/speaking/idle) and the `transcriptLog` rendered as a simple scrolling list — useful for foreground testing even though the real use case is screen-off.

- [ ] **Step 8: Verify in the browser preview**

With a real DeepSeek key configured and a seeded `state.learned` containing a few known words: start a call, speak (or, since browser mic input may not be practical in this preview, temporarily trigger the transcript-handling path directly via `javascript_tool` with a canned transcript string) a simple Mandarin-learner question, confirm: a reply is spoken, any `⟦...⟧`-tagged word in the raw reply resulted in a new `addConversationWord` call (check `localStorage` afterward), and the spoken text has the tags stripped. Then verify the empty-transcript and goodbye-phrase paths the same way, and verify a deliberately-broken API key produces the spoken fallback line instead of a crash. Background/device-level interruption behavior (Step 6) cannot be verified in this preview — note it as device-only verification, to be checked alongside Task 1's manual device test once this is on a real build.
